## 3. Issues and Bugs Found

Findings are not yet resolved; "Resolution" column reflects current status of each.

| Issue | Root Cause | Resolution | Files |
|-------|-----------|------------|-------|
| Hook chain fail-fast drops the entire log entry on first hook error | `hookChain.process` at hook.go:150 returns on first `err != nil`; callers (`Event.Emit` at event.go:232-235, presumably `logger.log`) treat that as a write-skip, with only an `fmt.Fprintf(os.Stderr, ...)` warning. Operators not watching stderr lose log records silently. | not fixed — awaiting decision on whether this is intended fail-closed-for-audit-safety or accidental data loss; either way undocumented | `hook.go:150`, `event.go:232-235` |
| `fileOutput.Close` panics on second invocation | `close(f.done)` is called on the rotation-stop channel; closing an already-closed channel is a Go runtime panic. `Logger.Close` is protected by a `closed.CompareAndSwap` at logger.go:364, but `Event.Close` has no such guard, and any user constructing a `fileOutput` via `MustFile` / `RotatingFile` directly and calling `Close` twice gets the panic. | not fixed — was listed as out-of-scope in the prior plan; restated here | `output.go` (`fileOutput.Close`) |
| `Event` Close-then-Emit ordering writes to closed outputs | The new `emitted atomic.Bool` (`979e59a`) blocks double-Emit but does not catch `Close` followed by `Emit`. After `Event.Close` returns, the underlying zap engine's tee of cores still references the now-closed outputs. A subsequent `Emit` would attempt a write to a closed file — undefined behavior. | not fixed — needs a `closed atomic.Bool` checked at the top of `Emit`, parallel to the existing emitted guard | `event.go` (`Emit`, `Close`) |
| PII recursion only matches `map[string]any`; `map[string]string` (and similar concrete map types) falls through to `default: continue` | `MaskFields` at pii.go's type switch only adds the `case map[string]any:` arm. `http.Header` (which is `map[string][]string`) and user-flattened `map[string]string` are common log shapes that hit this — they would not be recursed into for sensitive-field redaction. | not fixed — needs either an additional case (one type-switch arm, same recursion shape) or an explicit doc paragraph that only `map[string]any` is supported | `pii.go` (`MaskFields`, `MaskFieldsWithCounts`) |
| `containsFold` is ASCII-only by acknowledged design | The function comment notes "may miss" for non-ASCII case folds. Default sensitive-fields list is ASCII-safe (`senha` is ASCII), but user-supplied Portuguese fields like `endereço`, `cartão`, `não_compartilhar` won't match against an `Endereço` annotation key. For a library that ships Brazilian-locale defaults (CPF, CNPJ patterns), this is a real coverage gap for non-English deployments. | not fixed — needs either Unicode-aware fold (e.g. `golang.org/x/text/cases`) or an explicit limitation note in godoc | `pii.go` (`containsFold` near line 383+) |
| `Event.Emit` appends `e.errDetails` without cloning | event.go:219 does `entry.Annotations = append(cloneAnnotations(e.annotations), e.errDetails...)` — `e.errDetails` is appended verbatim. A hook that mutates the appended annotations would leak back to the `Event` struct's `errDetails` field. Not exploitable with current hooks (PII no longer mutates after `d4832f7`), but a custom `Hook` that does in-place mutation would break the invariant. | not fixed — minor; would tighten by cloning errDetails alongside annotations | `event.go:219` |
| `isSensitiveField` is O(M × name-length) per annotation | Iterates `m.fields` and calls `containsFold` per entry. Fine for typical configs (M = 5–15); would matter only at very high throughput with large field lists. Already listed in prior report's §6.3. | not fixed — only worth optimizing if benchmarks show it as a bottleneck | `pii.go:354-361` |
